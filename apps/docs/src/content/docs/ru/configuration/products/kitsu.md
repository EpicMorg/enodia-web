«Kitsu» — общеизвестное название стека для трекинга производства от
CG-Wire, но сам Kitsu — это Vue.js-фронтенд **без собственного эндпоинта
версии**. На `GET /api/status` — подтверждено вживую, в том числе на
хосте, буквально названном «kitsu» в DNS — отвечает на самом деле
[Zou](/ru/configuration/products/zou/), API-бэкенд, с которым общается
Kitsu. Указывайте `address` на тот же самый бэкенд, ровно как и для
`product: zou` — отдельного URL «для Kitsu» настраивать не нужно.

```yaml
targets:
  - id: kitsu-main
    product: kitsu
    address: https://kitsu.example.com
```

## Аутентификация

Отсутствует — эндпоинт не принимает никакого credential.

## Почему `kitsu` — отдельный продукт от `zou`, а не алиас

Оба указывают на идентичный бэкенд Zou и эндпоинт, но им нужны **разные
резолверы жизненного цикла**: собственный репозиторий `cgwire/zou` на
GitHub публикует только голые git-теги (подтверждено вживую — его
Releases API возвращает пустой список), которые резолвер GitHub Releases
в enodia прочитать не может вообще. У `cgwire/kitsu` есть настоящие
GitHub Releases, и это именно то, что реально нужно отслеживать
установке, которая воспринимает себя как «работающую на Kitsu». Номера
версий этих двух репозиториев действительно расходятся (бэкенд Zou
опережает Kitsu), поэтому сравнение под более «технически точным»
именем `zou` привело бы к молчаливому сравнению с версией не того
компонента — отсюда два зарегистрированных продукта, использующих одну
реализацию пробы, а не один продукт с алиасом.

## Записываемые поля

- `version`
- `extra.databaseUp`, `extra.keyValueStoreUp`, `extra.eventStreamUp`,
  `extra.jobQueueUp`, `extra.indexerUp` — флаги состояния компонентов,
  `"true"`/`"false"`

## Резолвер жизненного цикла

`github:cgwire/kitsu` — только последний релиз на GitHub; данных по
eol/support/lts нет (у GitHub нет мнения о политике жизненного цикла,
только «какой тег последний»).
