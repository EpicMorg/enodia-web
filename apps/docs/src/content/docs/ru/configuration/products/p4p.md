Запускает `p4 -Ztag -p <address> info` — та же команда и тот же
механизм внешнего CLI, что и у
[`p4d`](/ru/configuration/products/p4d/); почему это обращается к
собственному бинарнику `p4` оператора, а не говорит по wire-протоколу
Perforce напрямую, см. на той странице.

```yaml
targets:
  - id: p4p-main
    product: p4p
    address: p4p.example.com:1666
```

## Требует CLI `p4` на машине, где запущена enodia

Так же, как у [`p4d`](/ru/configuration/products/p4d/#требует-cli-p4-на-машине-где-запущена-enodia)
— переопределите путь к бинарнику через `options.binary`, если `p4` не
в `$PATH`:

```yaml
targets:
  - id: p4p-main
    product: p4p
    address: p4p.example.com:1666
    options:
      binary: /opt/perforce/bin/p4
```

## Аутентификация

Отсутствует — подтверждено вживую, что `info` отвечает полностью
анонимно на реальном продакшн-прокси.

## Проверка личности вендора

Прокси отвечает на `info` всем тем же, чем и прямой сервер, **плюс
собственное поле `proxyVersion`** — `serverVersion`/`ServerID`/
`serverServices` бэкенд-сервера проходят без изменений, описывая
сервер за прокси, а не сам прокси. Эта проба требует присутствия
`proxyVersion`, отклоняя ответ прямого сервера (у которого такого поля
нет), вместо того чтобы сообщить версию не того продукта — та же
проверка, что и у [`p4d`](/ru/configuration/products/p4d/), только в
обратную сторону.

## Записываемые поля

- `version` — например, `2024.2`, разобрано из формы `proxyVersion`:
  `P4P/LINUX26X86_64/2024.2/2832881 (2025/09/30)`
- `extra.raw` — полная неразобранная строка `proxyVersion`
- `extra.backendServerVersion`, `extra.backendServerID` — версия/ID
  самого бэкенд-сервера `p4d`, переданные из того же ответа, если
  присутствуют

## Резолвер жизненного цикла

Отсутствует — Perforce проприетарен, у endoflife.date нет страницы ни
под одним из опробованных слагов (подтверждено 404), и нет публичных
релизов на GitHub, на которые можно было бы опереться. Пока только
инвентаризация — так же, как у
[`p4d`](/ru/configuration/products/p4d/).
