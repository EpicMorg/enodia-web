Начиная с 2.0, enodia показывает, какие известные уязвимости затрагивают
ровно ту версию, которую сообщил каждый таргет, — вместе с осями
patch/lifecycle/branch, а не вместо них. Сверка идёт по двум публичным
базам:

- **БДУ ФСТЭК** — банк данных угроз ФСТЭК России,
  [bdu.fstec.ru](https://bdu.fstec.ru/).
- **NIST NVD** — американская National Vulnerability Database,
  [nvd.nist.gov](https://nvd.nist.gov/).

Каждый источник работает и в одиночку; если настроены оба, их находки
объединяются по CVE.

Начиная с 2.2, к ним добавляются собственные данные безопасности четырёх
вендоров там, где они их публикуют: MariaDB, Atlassian (Jira, Confluence,
Bitbucket, Bamboo), PostgreSQL и nginx — см.
[Собственные данные вендоров](#собственные-данные-вендоров).

Начиная с 2.1, десять дистрибутивов Linux сверяются ещё и **по каждому
установленному пакету** с собственными данными безопасности их
вендоров — Debian Security Tracker, OVAL-файлами вендоров и secdb Alpine
(см. [CVE на уровне пакетов для дистрибутивов Linux](#cve-на-уровне-пакетов-для-дистрибутивов-linux)).

Всё это опционально: конфиг без блока `cve:` ведёт себя ровно так же,
как в 1.x, и каждый источник работает сам по себе.

## Скачивание баз

enodia сверяется только с локальными файлами. `check`, `collect` и
`serve` никогда ничего не скачивают — та же логика закрытого контура,
что и в [двухфазном дизайне](/ru/concepts/#две-фазы-намеренно-разделяемые):
машине, на которой запускается `check`, для сверки с CVE не нужен
интернет, нужна только копия файлов. Начиная с 2.2, их скачивает одна
отдельная команда, и только когда вы её запускаете: `enodia cve update`.
Или скачайте их сами, как описано ниже для каждого источника, — файлы в
обоих случаях одни и те же.

### `enodia cve update`

```bash
enodia cve update                         # каждый cve.*.path в активном конфиге
enodia cve update --from inventory.jsonl  # плюс то, что нужно хостам этого инвентаря
enodia cve update --dry-run               # показать, что было бы скачано, ничего не скачивая
```

В каждый настроенный `cve.*.path` она скачивает то, что читает эта
запись:

- **БДУ** — `vulxml.zip`. Здесь `cve.bdu.path` должен быть `.zip`;
  формы `.xml` и `.tar.gz`, которые сверка тоже принимает, — это ваша
  собственная переупаковка, `update` их не создаёт.
- **NVD** — файл текущего года, прошлого и всех лет, которых ещё нет на
  диске; `--all-years` обновляет все годы (NVD ежедневно пересобирает
  все годовые файлы). `cve.nvd.path` должен быть директорией.
- **Debian** — `.json` трекера.
- **OVAL, secdb Alpine, страницы PostgreSQL по мажорным версиям** — по
  одному файлу на релиз, поэтому релизы берутся из трёх мест: из файлов,
  уже лежащих в директории, из инвентарей, переданных через `--from`
  (какие релизы работают на их хостах), и из `--oval`, `--alpine` и
  `--postgresql`. `cve.oval.path` и `cve.alpine.path` должны быть
  директориями; `cve.postgresql.path`, указывающий на файл, получает
  только главную страницу.
- **MariaDB, Atlassian, nginx** и главная страница PostgreSQL — по
  одному файлу.

| Флаг | Скачивает |
|---|---|
| `--from <inventory>` | релизы OVAL, ветки Alpine и мажорные версии PostgreSQL, нужные хостам этого инвентаря (можно повторять) |
| `--oval <release>` | один релиз OVAL: `ubuntu:<codename>`, `rhel:<N>`, `almalinux:<N>`, `oracle-linux:<N>`, `astra-linux:<X.Y>`, `redos:<X.Y>` (можно повторять) |
| `--alpine <branch>` | secdb одной ветки Alpine, например `v3.22` (можно повторять) |
| `--postgresql <major>` | собственную страницу безопасности одной мажорной версии PostgreSQL, например `13` (можно повторять) |
| `--all-years` | все годы NVD, а не только текущий, прошлый и недостающие |
| `--dry-run` | показать, что было бы скачано, ничего не скачивая |

Каждый файл запрашивается с If-Modified-Since по его копии на диске,
скачивается в `.enodia-update/` рядом с ней, **загружается тем же кодом,
что и при сверке с CVE**, и только после этого заменяет старую копию —
обрезанный zip или HTML-страница с ошибкой никогда не заменит рабочий
файл. Неизменившийся файл стоит одного запроса (MariaDB, PostgreSQL и
Atlassian не отдают Last-Modified, поэтому их файлы скачиваются заново
и сравниваются). Сетевые ошибки, 429 и 5xx повторяются дважды. Одна
неудача не останавливает остальные; код выхода — `1`, если не удалось
скачать хотя бы один файл. Запускайте её из cron — следующий цикл
`check` или `serve` подхватит новые файлы.

TLS проверяется по доверенным корневым сертификатам системы плюс тому,
что добавляет блок `cve.update`:

```yaml title="enodia.yaml"
cve:
  update:
    ca_file: /etc/enodia/russian-trusted.pem  # добавляется к системным корневым: PEM (один или несколько) или DER
    ca_dir: /etc/enodia/ca                    # каждый файл сертификата в ней, аналогично
    tls_skip_verify: false                    # true: не проверять ничего, для всех скачиваний
```

Для bdu.fstec.ru это необходимо: его цепочка заканчивается на Russian
Trusted Root CA, которого почти нет в хранилищах доверия, а сервер не
отдаёт свой промежуточный сертификат (см. [БДУ ФСТЭК](#бду-фстэк) ниже).
Без того и другого скачивание БДУ падает с `certificate signed by
unknown authority`, а остальные файлы всё равно скачиваются. Root CA и
Sub CA 2024 года опубликованы по адресам
`http://nuc-cdp.digital.gov.ru/cdp/rootca_ssl_rsa2022.crt` и
`http://nuc-cdp.digital.gov.ru/cdp/subca_ssl_rsa2024.crt`; файл, в
который склеены оба, подходит как `ca_file`.

Файлы она называет так же, как ручные команды ниже (`v3.22-main.json`,
`13.html`, …), так что оба способа можно совмещать. Хосты, к которым
она обращается, перечислены на странице
[Конфиденциальность](/ru/privacy/).

### БДУ ФСТЭК

Один файл — полная выгрузка ФСТЭК (около 33 МБ в архиве):

```bash
curl -fL --cacert ru-chain.pem \
  -o /var/lib/enodia/cve/bdu/vulxml.zip \
  https://bdu.fstec.ru/files/documents/vulxml.zip
```

У bdu.fstec.ru сертификат национального удостоверяющего центра
Минцифры, которого нет в обычных системных хранилищах доверия, — простой
`curl` падает с ошибкой сертификата. Кроме того, сервер не отдаёт свой
промежуточный сертификат, а `curl` (в отличие от браузера) недостающий
сам не скачивает, поэтому одного установленного корневого мало. Соберите
бандл из корневого и того промежуточного, на который ссылается
сертификат сайта:

```bash
curl -fsS -o root.crt https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt
curl -fsS -o sub.crt  http://nuc-cdp.digital.gov.ru/cdp/subca_ssl_rsa2024.crt
{ cat root.crt; echo; cat sub.crt; } > ru-chain.pem
```

Проверено вживую 2026-09-23. Если перестанет работать — скорее всего,
промежуточный сертификат сменили: актуальный указан в поле *Authority
Information Access* сертификата самого сайта (`openssl s_client
-connect bdu.fstec.ru:443 | openssl x509 -noout -ext authorityInfoAccess`).
`curl -k` файл тоже скачает, но без проверки того, что вы затем
подкладываете в свой отчёт по безопасности.

### NIST NVD

По одному файлу на год, `nvdcve-2.0-<год>.json.gz`, с 2002 по текущий.
Сложите нужные в одну директорию:

```bash
mkdir -p /var/lib/enodia/cve/nvd && cd /var/lib/enodia/cve/nvd
for y in $(seq 2002 "$(date +%Y)"); do
  curl -fsSLO "https://nvd.nist.gov/feeds/json/cve/2.0/nvdcve-2.0-$y.json.gz"
done
```

Файл текущего года обновляется ежедневно, прошлые годы — редко. У
каждого файла есть сопутствующий `.meta` (`nvdcve-2.0-<год>.meta`) с
размером и `sha256` — обратите внимание, хеш считается от
**распакованного** JSON, а не от `.gz`.

### Debian Security Tracker

Один файл — полная JSON-выгрузка трекера (около 80 МБ), для таргетов
`debian`:

```bash
curl -fsSL -o /var/lib/enodia/cve/debian.json \
  https://security-tracker.debian.org/tracker/data/json
```

Подойдут и копии `.json.gz` и `.json.zip`.

### OVAL вендоров

По одному файлу на каждый релиз дистрибутива в вашем парке, все в одной
директории, для таргетов `ubuntu`, `linuxmint`, `rhel`, `rocky-linux`,
`almalinux`, `oracle-linux`, `astra-linux` и `redos`:

| Таргеты | Файл |
|---|---|
| Ubuntu, Linux Mint (его база Ubuntu) | `https://security-metadata.canonical.com/oval/com.ubuntu.<codename>.usn.oval.xml.bz2` |
| RHEL **и Rocky Linux** | `https://security.access.redhat.com/data/oval/v2/RHEL<N>/rhel-<N>.oval.xml.bz2` |
| AlmaLinux | `https://security.almalinux.org/oval/org.almalinux.alsa-<N>.xml.bz2` |
| Oracle Linux | `https://linux.oracle.com/security/oval/com.oracle.elsa-ol<N>.xml.bz2` |
| Astra Linux SE 1.7, 1.8 | `https://dl.astralinux.ru/astra/oval/<1.7\|1.8>_x86-64/oval-definitions-alse-<1.7\|1.8>.xml` |
| РЕД ОС 7.3, 8.0 | `https://redos.red-soft.ru/support/secure/<7.3\|8.0>/redos.xml` |

```bash
mkdir -p /var/lib/enodia/cve/oval && cd /var/lib/enodia/cve/oval
curl -fsSLO https://security-metadata.canonical.com/oval/com.ubuntu.noble.usn.oval.xml.bz2
curl -fsSLO https://security.access.redhat.com/data/oval/v2/RHEL9/rhel-9.oval.xml.bz2
curl -fsSL -o redos-8.0.xml https://redos.red-soft.ru/support/secure/8.0/redos.xml
```

Файлы берутся в том виде, как их публикуют, `.xml` или `.xml.bz2`. Для
какого релиза файл, определяется по его содержимому, а не по имени, —
поэтому двум файлам РЕД ОС, которые оба публикуются как `redos.xml`,
нужны лишь разные имена на диске. Два файла отклоняются намеренно, с
ошибкой, которая называет файл, который нужно использовать вместо них:

- **Собственный OVAL Rocky Linux** (`org.rockylinux.rlsa-<N>.xml`) — в
  нём лишь малая часть бюллетеней Rocky, и он не проходит проверку по
  схеме OVAL. Rocky пересобирает пакеты Red Hat с теми же версиями,
  поэтому хосты Rocky сверяются по файлу Red Hat.
- **Вариант Ubuntu `oci.`** — он проверяет файл состояния dpkg
  регулярными выражениями вместо пакетов.

Все адреса проверены вживую 2026-10-02.

### secdb Alpine

По два файла на каждую ветку Alpine в вашем парке, `main` и
`community`, для таргетов `alpine-linux`. Имена у разных веток
совпадают, поэтому сохраняйте их под разными:

```bash
mkdir -p /var/lib/enodia/cve/alpine && cd /var/lib/enodia/cve/alpine
for b in v3.20 v3.22; do
  for r in main community; do
    curl -fsSL -o "$b-$r.json" "https://secdb.alpinelinux.org/$b/$r.json"
  done
done
```

## Конфигурация

Блок `cve:` в `enodia.yaml` — не в `settings.yaml`, поскольку он меняет
саму оценку, а не только отображение:

```yaml title="enodia.yaml"
schemaVersion: 1
cve:
  bdu:
    path: /var/lib/enodia/cve/bdu/vulxml.zip
  nvd:
    path: /var/lib/enodia/cve/nvd
  debian:
    path: /var/lib/enodia/cve/debian.json
  oval:
    path: /var/lib/enodia/cve/oval
  alpine:
    path: /var/lib/enodia/cve/alpine
  mariadb:
    path: /var/lib/enodia/cve/mariadb.md
  atlassian:
    path: /var/lib/enodia/cve/atlassian.json
  postgresql:
    path: /var/lib/enodia/cve/postgresql
  nginx:
    path: /var/lib/enodia/cve/nginx.html
targets:
  - id: gitlab-main
    product: gitlab
    address: https://gitlab.example.com
    credentials: gitlab-token
```

| Поле | Принимает |
|---|---|
| `cve.bdu.path` | `.xml`, `.zip` (выгрузка в том виде, как её публикуют) или `.tar.gz`/`.tgz` |
| `cve.nvd.path` | один файл `.json`, `.json.gz` или `.json.zip`, либо директорию с ними |
| `cve.debian.path` | выгрузку трекера: `.json`, `.json.gz` или `.json.zip` |
| `cve.oval.path` | один OVAL-файл (`.xml` или `.xml.bz2`) либо директорию с ними |
| `cve.alpine.path` | один `.json`-файл secdb либо директорию с ними |
| `cve.mariadb.path` | `community-server.md` от MariaDB, сохранённый как есть |
| `cve.atlassian.path` | JSON vuln-transparency от Atlassian, сохранённый как есть |
| `cve.postgresql.path` | страницу безопасности PostgreSQL в HTML либо директорию с такими страницами |
| `cve.nginx.path` | `security_advisories.html` от nginx, сохранённый как есть |
| `cve.update` | параметры TLS только для [`enodia cve update`](#enodia-cve-update): `ca_file`, `ca_dir`, `tls_skip_verify` |

Относительные пути резолвятся относительно директории того конфига,
в котором они указаны, — так же, как `credentials_file`. Блок читается
из того конфига, который реально использует запуск, — `--config`,
`$ENODIA_CONFIG` или [стандартные пути поиска](/ru/configuration/#расположение-файлов).
Это касается и `check --from inventory.jsonl`: инвентарь, собранный в
закрытом контуре, сверяется там, где запускается `check`, если там
находится конфиг с блоком `cve:`. Если конфиг не найден вовсе,
`check --from` всё равно работает, просто без CVE.

**Указанный путь, которого не существует, — это ошибка**, а не тихий
пропуск: `check` завершается с `stat ...: no such file or directory`,
а не выдаёт отчёт, в котором CVE просто молча отсутствуют. Начиная с
2.1, `enodia config validate` тоже проверяет, что каждый указанный путь
существует, так что опечатка видна уже там (начиная с 2.2 — и
`cve.update.ca_file` и `ca_dir`). Разбирается ли файл на самом деле,
по-прежнему выясняется только тогда, когда запуск его загружает, — или
когда его скачивает `enodia cve update`.

:::caution[Пути Windows]
Пишите путь Windows без кавычек, в одинарных кавычках, с прямыми
слешами или как UNC-путь. В **двойных** кавычках YAML `\t` и `\n`
превращаются в табуляцию и перевод строки — `"C:\tmp\bdu.zip"` молча
указывал бы не туда, поэтому enodia отклоняет путь с управляющим
символом ещё при загрузке, с подсказкой.
:::

## Первый запуск и кеш

БДУ и NVD разбираются потоково, результат кешируется в системной
директории кеша (`$XDG_CACHE_HOME/enodia/cve`, по умолчанию
`~/.cache/enodia/cve` в Linux; `~/Library/Caches/enodia/cve` в macOS;
`%LocalAppData%\enodia\cve` в Windows). Первый запуск после изменения
файла разбирает его целиком — около минуты на весь NVD плюс БДУ; замер
2026-09-23 на БДУ плюс одном файле NVD за 2026 год — 25 с. Все
следующие запуски читают кеш: 0,2 с на тех же данных, кеш 11 МБ. TTL
нет — ключ кеша строится по самим файлам (размер и время изменения) и
по собственным таблицам продуктов enodia, поэтому замена файла,
добавление года в директорию NVD или обновление enodia сами вызывают
пересборку.

Разобранный OVAL кешируется так же — около 11 с на разбор файлов Ubuntu
noble, RHEL 9, AlmaLinux 9 и Oracle Linux 9 вместе, большая часть из них
уходит на bzip2. Выгрузка трекера Debian (около секунды на разбор) и
secdb Alpine (несколько сотен КБ) не кешируются. Со всеми источниками
сразу (БДУ, NVD, Debian, восемь OVAL-файлов, Alpine) в апстриме
намерили около 22 с на `check` без кеша и 3,4 с с кешем, с пиком
0,5–0,6 ГБ памяти — меньше, если в `cve.oval.path` лежат только те
релизы, которые у вас реально есть.

`enodia serve` перечитывает блок `cve:` и файлы на каждом цикле
`--interval` (дёшево, из кеша), так что замена файлов по cron начинает
действовать без перезапуска сервера.

## Где видны находки

- **`check`** — колонка `CVES` в [представлениях `compact` и
  `drift`](/ru/views/): число различных CVE, затрагивающих именно эту
  версию. `-` означает, что находок нет: ни одна не затрагивает эту версию,
  нет блока `cve:` или продукт не сопоставляется (см. ниже); сама
  колонка есть всегда. У `lifecycle` и `fleet` этой колонки
  нет.
- **`export --format html`** — та же колонка со ссылкой, открывающей
  список по таргету: одна строка на CVE, самые опасные сверху, со
  ссылками на NVD, cve.org и, для находок из БДУ, на страницу
  bdu.fstec.ru; русский текст из БДУ, если CVE есть в БДУ, иначе
  английское описание из NVD; оценка — цветными бейджами, например
  `CRITICAL · CVSS 3.1 9.8`. Находки по пакетам — одна строка на пакет:
  `linux 6.12.107-1 → 6.12.111-1`, со ссылкой на бюллетень с
  исправлением и свёрнутым под ней списком CVE. Сделано на чистом CSS —
  офлайн-отчёт по умолчанию по-прежнему не содержит JavaScript вообще.
- **`export --format json`** — каждая находка каждого источника целиком,
  в массиве `cves` у каждой оценки: источник (`bdu`, `nvd` или вендорский:
  `mariadb`, `atlassian`, `postgresql`, `nginx`),
  идентификатор бюллетеня, идентификаторы CVE, заголовок, собственная
  текстовая оценка источника, сопоставленное имя продукта или CPE,
  диапазон версий и разобранная оценка CVSS. В отличие от таблицы и
  HTML-списка, где одна строка — один CVE, JSON хранит находку каждого
  источника отдельно: один и тот же CVE может встретиться один раз из
  БДУ и по разу на каждый подходящий CPE из NVD. Находки по пакетам
  (источник `debian`, `oval` или `alpine`) несут ещё установленную и
  исправленную версии — см. [Отчёты](/ru/reporting/#--format-json).
- **`export --format prometheus`** — без данных о CVE.

**CVE не влияют ни на severity, ни на код выхода.** `SEVERITY`
по-прежнему считается только по осям patch/lifecycle/branch, и
`--fail-on` тоже знает только эти три оси — находка остаётся фактом,
который стоит посмотреть, а не вердиктом, вынесенным enodia за вас.
Нужно ли и как CVE должен повышать severity — открытый вопрос в
апстриме.

## Какие продукты сопоставляются

91 из 123 продуктов: 81 — по имени продукта в БДУ и NVD (шесть из них —
ещё и по собственным данным вендора, см. [ниже](#собственные-данные-вендоров)),
каждое имя вендора/продукта сверено дословно по реальным полным
выгрузкам, и 10
дистрибутивов Linux — по каждому установленному пакету (см. следующий
раздел). Источники для каждого указаны на его собственной странице в
разделе [Настройка продуктов](/ru/products/).

Не сопоставляются, и у каждого случая своя причина:

- **Остальные дистрибутивы Linux общего назначения** (Fedora, CentOS
  Stream, Amazon Linux, openSUSE, …) — их CVE относятся к пакетам, номер
  релиза не говорит, какие пакеты с тех пор обновлены, а источника на
  уровне пакетов для них пока нет.
- **BSD-системы и Oracle Solaris** — NVD хранит их уровень патчей
  (`-p5` у FreeBSD, errata у OpenBSD) в поле CPE, которое этот механизм
  не читает; сверка только по релизу приписала бы полностью
  пропатченному хосту все CVE, когда-либо исправленные в этом релизе.
- **ESXi и vCenter** — та же проблема: почти все записи вида `7.0` +
  `update_1`.
- **TrueNAS** — слишком мало записей, с другой нумерацией, чем сообщает
  проба.
- **Нет пригодных данных ни в одном источнике** — Kitsu, Zou,
  postgres_exporter, Perforce Proxy, Perforce Helix Swarm, Supermicro
  BMC, LibreTranslate, TorrServer и Euro-Office (форк без собственных
  записей).
- **PostHog** — границы в NVD у него — git-коммиты, а не версии.
- **`generic`** — у самописного парсера нет идентичности продукта, по
  которой можно искать.

## CVE на уровне пакетов для дистрибутивов Linux

Номер релиза не говорит, какие пакеты на хосте с тех пор обновлены,
поэтому эти десять дистрибутивов сверяются по каждому установленному
пакету. Их пробы в том же SSH-обращении, что и за версией, читают
установленные пакеты и работающее ядро, и каждый пакет сверяется с
собственными данными безопасности дистрибутива:

| Проба | Источник | Ключ |
|---|---|---|
| `debian` | Debian Security Tracker | `cve.debian.path` |
| `ubuntu` | OVAL Canonical | `cve.oval.path` |
| `linuxmint` | OVAL Canonical, для его базы Ubuntu | `cve.oval.path` |
| `rhel`, `rocky-linux` | OVAL Red Hat | `cve.oval.path` |
| `almalinux` | OVAL AlmaLinux | `cve.oval.path` |
| `oracle-linux` | OVAL Oracle | `cve.oval.path` |
| `astra-linux` | OVAL Astra Linux (SE 1.7, 1.8) | `cve.oval.path` |
| `redos` | OVAL РЕД ОС (7.3, 8.0) | `cve.oval.path` |
| `alpine-linux` | secdb Alpine | `cve.alpine.path` |

**Сообщаются только CVE, для которых уже есть исправление новее
установленного**, — то, что закроет обновление (а для ядра —
перезагрузка). CVE, которые вендор ещё не исправил, не показываются:
они одинаковы на всех хостах релиза, сделать с ними ничего нельзя, и
они бы похоронили под собой те, с которыми можно что-то сделать.

**Одна находка на пакет, а не на CVE.** Одно отстающее ядро может нести
больше тысячи CVE; список по одному CVE было бы невозможно читать.
Каждая находка называет пакет, его установленную версию, версию, которая
закрывает все его CVE, и бюллетень с этим исправлением (USN, RHSA, ALSA,
ELSA, бюллетень Astra, ROS или страница трекера Debian/Alpine). Колонка
`CVES` по-прежнему считает CVE, а не пакеты.

**Версии сравниваются по правилам каждого пакетного менеджера** —
порядок версий dpkg, rpm и apk, сверенный в апстриме с `apt_pkg`, rpm и
apk-tools на тысячах реальных пар версий для каждого, — с учётом потоков
модулей AppStream (пакет сверяется только с исправлениями своего
потока), архитектуры Oracle Linux, вариантов FIPS и Ksplice и
**работающего** ядра, а не тех пакетов ядра, что просто установлены.
Каждый источник сверен в апстриме с `oscap oval eval`,
`dnf updateinfo`, python3-apt или `apk version -t` на реальных хостах и
контейнерах, с идентичным результатом.

**Proxmox VE** получает находки по пакетам как второй таргет:
SSH-таргет [`debian`](/ru/configuration/products/debian/) на том же
хосте, рядом с его API-таргетом
[`proxmox`](/ru/configuration/products/proxmox/). Пакет Debian `linux`
сопоставляется только с работающим ядром Debian, так что собственное
ядро Proxmox за него не принимается.

### Учёт редакции

GitLab, HashiCorp Vault, Nextcloud и MongoDB публикуют отдельные списки
CVE для community- и enterprise-редакций. Их пробы записывают редакцию
сервера в `extra.enterprise`, и community-инстанс больше не видит
находок только для enterprise — на реальных данных GitLab 19.2.2 CE
видит 4 из 9 находок NVD, Nextcloud 27.1.3 CE — 11 из 23. Если редакция
неизвестна (старый сервер её не сообщает), сохраняются все находки.

Начиная с 2.2, ещё у нескольких продуктов сама версия говорит, к какой
линейке или редакции относится диапазон:

- **Jenkins** — weekly- (`2.580`) и LTS-релизы (`2.568.3`) получают одно
  и то же исправление под разными номерами, и обе базы пишут диапазон
  для каждого. Линейку выбирает форма версии (две части — weekly, три —
  LTS), так что исправленный LTS больше не помечается weekly-границей
  того же исправления.
- **Splunk** — применяются только диапазоны Splunk Enterprise (какой это
  продукт, говорит собственный `product_type` splunkd); Splunk Cloud не
  сопоставляется.
- **pfSense** — проба сообщает только Community Edition, поэтому
  диапазоны pfSense Plus никогда не применяются.
- **WAPT** — собственная редакция сервера (`community` или `enterprise`)
  передаётся как есть.
- **Kafka** — сборка Confluent Platform (`7.6.1-ccs`) остаётся без
  сверки: по своей нумерации она выглядела бы новее любой границы Apache
  Kafka.

### Dell iDRAC и Synology DSM

**iDRAC**: обе базы называют каждое поколение iDRAC отдельным продуктом,
а номера прошивок у них пересекаются (iDRAC7 и iDRAC8 оба работают на
2.x, с разными исправлениями). Поколение определяется по `extra.model`
пробы — собственной строке модели из Redfish: 11G — это iDRAC6, 12G —
iDRAC7, 13G — iDRAC8, 14G–16G — iDRAC9, 17G — iDRAC10. Без модели
сверяется только прошивка 3.x и новее — это может быть только iDRAC9.

**Synology DSM**: релиз — это версия, сборка и Update: Synology пишет
`DSM 7.2.1-69057 Update 6`, NVD и БДУ — `7.2.1-69057-6`. Начиная с 2.2,
проба записывает Update ещё и в `extra.update`, и обе стороны сводятся к
одной сравнимой версии. Инвентарь, собранный до 2.2, не содержит
`extra.update` и читается как Update 0: исправленные Update могут быть
помечены, но ни один не будет пропущен.

### SSH

Проба [`ssh`](/ru/configuration/products/ssh/) охватывает любую
реализацию SSH, поэтому сопоставление идёт по баннеру: `OpenSSH_…` ищется
как OpenSSH, `dropbear_…` — как Dropbear, а любой другой SSH-стек
остаётся без сверки, а не получает чужие CVE от OpenSSH.

## Собственные данные вендоров

БДУ и NVD часто описывают исправление в одной ветке как открытый
диапазон («до 11.4.10»), который тогда накрывает и все более старые
ветки — включая исправленные релизы и ветки, где этой ошибки никогда не
было. Четыре вендора сами публикуют достоверные данные по веткам, и
enodia читает их рядом с БДУ и NVD с одним дополнительным правилом:
**по CVE, который известен данным вендора, решают они** — находка БДУ
или NVD, все CVE которой вендор охватывает и для этой версии не
помечает, отбрасывается. CVE, которых у вендора нет, по-прежнему
берутся из БДУ и NVD.

| Ключ | Продукты | Источник |
|---|---|---|
| `cve.mariadb.path` | `mariadb` | таблица исправленных CVE MariaDB |
| `cve.atlassian.path` | `jira`, `confluence`, `bitbucket`, `bamboo` | данные Atlassian об уязвимостях по каждому релизу |
| `cve.postgresql.path` | `postgresql` | страницы безопасности PostgreSQL |
| `cve.nginx.path` | `nginx` | бюллетени безопасности nginx |

Без этих ключей продукты всё равно сверяются с одними БДУ и NVD — с
описанной выше проблемой перекрытия.

### MariaDB

MariaDB одновременно поддерживает пять-шесть серий релизов. На реальных
версиях из парка диапазоны БДУ и NVD помечали последние, полностью
пропатченные релизы поддерживаемых серий (10.11.19, 11.4.13), а те же
две базы при этом пропускали 9 из 21 CVE, которые сама MariaDB
перечисляет для 10.11.8.

`cve.mariadb.path` добавляет собственную таблицу исправленных CVE
MariaDB, в которой исправляющий релиз указан **для каждой серии**. CVE,
которых в таблице нет (новее скачанной копии, только из БДУ или без
идентификатора CVE), по-прежнему берутся из БДУ и NVD.

Как читается таблица:

- Серия со своим исправлением уязвима от первого релиза до этого
  исправления.
- Серия без своего исправления, которая ещё поддерживалась, когда CVE
  исправили в другой серии, не затронута — MariaDB исправляет все живые
  серии вместе.
- Серия, которая к тому моменту уже закончилась, помечается для всех
  своих релизов, а релизом для перехода указывается наименьшее
  исправление в более новой серии (об этом говорит `FixStatus`). Это
  сознательный перекос в сторону лишней находки, и только для
  закончившихся серий.

### Atlassian

Выгрузка Atlassian перечисляет каждый релиз Jira Software, Jira Core,
Confluence, Bitbucket и Bamboo (Server и Data Center) с CVE, которые его
затрагивают, и релизом, исправляющим каждый из них, — **включая CVE
сторонних зависимостей**, которых записи NVD по Atlassian никогда не
перечисляют. Проба не отличает Server от Data Center, поэтому читаются
оба списка. Jira Service Management нумерует релизы по-своему и не
сопоставляется; релиз-кандидаты и EAP пропускаются.

Таргет оценивается **в пределах своей ветки major.minor**: от
затронутого релиза до следующего, указанного как исправляющий, или до
конца ветки, если исправления после него нет. Jira 10.3.26 не
помечается CVE, который Atlassian указывает только для 10.1 и 11.3.
Поскольку Atlassian перечисляет релизы поштучно, её вердикт действует
только для релиза, который в списке есть, — у релиза новее вашей копии
файла остаются находки БДУ и NVD. В апстриме намерили, что у новейшего
релиза каждой поддерживаемой ветки находок Atlassian нет, а у более
старых их становится намного больше: у Jira 10.3.12 было 4 CVE, стало
119 — почти все в зависимостях, исправленных в более поздних релизах
10.3.

### PostgreSQL

Страница безопасности называет для каждого CVE поддерживаемые мажорные
версии, которые он затрагивает, и исправление в каждой. Её вердикт
охватывает только мажорные версии, названные на сохранённых страницах:
главная страница перечисляет только поддерживаемые сейчас, поэтому для
закончившейся мажорной версии (13, 9.6) сохраните её собственную
страницу в ту же директорию — без неё у этой версии остаются находки БДУ
и NVD. Мажорная версия, закончившаяся ещё до выхода CVE, помечается без
исправления, если CVE распространяется на самую старую мажорную версию,
которая тогда ещё поддерживалась, — как и закончившиеся серии MariaDB.
Строки `packaging` (инсталлятор или сборка RPM) учитываются, но не
помечаются. В апстриме намерили, что у текущих релизов 18/17/16/15/14
было до 55 находок БДУ у каждого, а стало ни одной.

### nginx

Каждый бюллетень перечисляет уязвимые версии и, для каждой ветки, первый
исправленный релиз (`1.31.3+, 1.30.4+`): стабильный 1.30.5 больше не
помечается диапазоном, записанным до исправления в mainline. Ветки, так
и не получившие исправления, остаются помеченными; бюллетени только для
nginx/Windows пропускаются.

## Известные ограничения

- **БДУ может давать лишние находки между ветками.** Одна запись БДУ
  часто перечисляет отдельный диапазон на каждую поддерживаемую ветку, и
  у всех общая нижняя граница, поэтому версия, которая уже является
  исправлением в своей ветке, может попасть в более широкий диапазон
  соседней (задокументированный пример — Confluence 8.3.3 и
  CVE-2023-22515; так же ведут себя диапазоны Synology DSM по веткам —
  DSM 7.2.1-69057 Update 8 получает 5 находок БДУ). У диапазонов NVD для того же CVE есть собственные
  нижние границы, и этой проблемы нет. enodia сознательно предпочитает
  показать находку, которую стоит перепроверить, чем молча пропустить
  настоящую.
- **Записи NVD без каких-либо ограничений по версии отбрасываются.** По
  замерам на полных выгрузках это почти всегда были CVE десятилетней
  давности, привязанные к текущим релизам; цена — редкий действительно
  ещё не исправленный CVE, записанный таким образом.
- **У сверки по пакетам свои пробелы.** Трекер Debian охватывает только
  релизы, которые ещё поддерживает команда безопасности Debian
  (bookworm, trixie, testing, sid), — более старые хосты находок по
  пакетам не получают. У Alpine edge нет номерной ветки, и находок у
  него тоже нет. OVAL не интерпретируется полностью: ключи подписи
  пакетов не проверяются, поэтому сторонний пакет с именем пакета
  дистрибутива сравнивается так, будто он из дистрибутива. Пакеты ядра
  Astra Linux сравниваются как установленные, а не как работающие.
- **Условия NVD на несколько продуктов** («уязвимо только вместе с
  библиотекой Y») не вычисляются — проба сообщает один продукт на
  таргет, поэтому каждая уязвимая запись для сопоставленного продукта
  учитывается сама по себе.
