Читає `GET /CHANGELOG` — файл журналу змін, який DomainMOD постачає у
своєму веб-корені й який віддається як статичний файл. Схема за
замовчуванням — `https`.

```yaml
targets:
  - id: domainmod-main
    product: domainmod
    address: https://domains.example.com
```

До DomainMOD, встановленого за підшляхом (`DOMAINMOD_WEB_ROOT`), можна
звернутися, вказавши цей шлях в адресі, напр.
`https://www.example.com/domainmod`.

## Чому CHANGELOG

DomainMOD показує `Version 4.23.0` лише в нижньому колонтитулі макета для
користувачів, що увійшли в систему. CHANGELOG анонімний: він починається з
`DomainMOD CHANGELOG`, лінії-розділювача, а далі йдуть записи, найновіший
першим — `v4.23.0     2025-01-04`. Проба вимагає цього заголовка, щоб
журнал змін іншого застосунку не було прочитано як журнал DomainMOD.
Вебсервер, що блокує цей файл, робить ціль «не підтримується».

## Автентифікація

Немає — проба читає статичний файл і не приймає жодного виду облікових
даних. Починаючи з 2.2.0, облікові дані, налаштовані для цієї цілі, є
помилкою конфігурації, а не ігноруються; див.
[Конфігурація → Облікові дані](/uk/configuration/#облікові-дані).

## Записувані поля

Лише `version` — напр. `4.23.0`, з найновішого запису CHANGELOG
`v4.23.0     2025-01-04` (підтверджено наживо на `domainmod/domainmod:latest`,
чий `software.inc.php` містить `SOFTWARE_VERSION = '4.23.0'`). Ця проба не
записує полів `extra`.

## Зіставлення з CVE

Зіставляється з NVD, якщо налаштовано [блок `cve:`](/uk/cve/).

## Резолвер життєвого циклу

`github:domainmod/domainmod` — endoflife.date не має календаря DomainMOD
(підтверджено 404), тому резолвінг натомість виконується через GitHub
Releases: лише останній опублікований тег, що не є пре-релізом, без дат
eol/support/lts (GitHub не має позиції щодо політики життєвого циклу, лише
«який реліз останній»).
