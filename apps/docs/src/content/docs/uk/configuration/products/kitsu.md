«Kitsu» — загальновідомий бренд стеку CG-Wire для відстеження
виробництва, але сам Kitsu — це фронтенд на Vue.js **без власного
ендпоінта версії**. Насправді на `GET /api/status` відповідає — підтверджено
наживо, зокрема на хості, який у DNS буквально називається «kitsu», —
[Zou](/uk/configuration/products/zou/), API-бекенд, з яким взаємодіє Kitsu.
Вкажіть в `address` той самий бекенд, точно так само, як для `product:
zou`, — окремого URL «Kitsu» для налаштування немає.

```yaml
targets:
  - id: kitsu-main
    product: kitsu
    address: https://kitsu.example.com
```

## Автентифікація

Немає — ендпоінт не приймає жодного виду облікових даних.

## Чому `kitsu` — окремий від `zou` продукт, а не псевдонім

Обидва вказують на той самий бекенд Zou і той самий ендпоінт, але їм
потрібні **різні резолвери життєвого циклу**: власний GitHub-репозиторій
`cgwire/zou` публікує лише голі git-теги (підтверджено наживо — його
Releases API повертає порожній список), які резолвер GitHub Releases в
enodia взагалі не може прочитати. `cgwire/kitsu` має справжні GitHub
Releases, і саме їх насправді потрібно відстежувати для розгортання, яке
вважає, що «працює на Kitsu». Номери версій двох репозиторіїв справді
розходяться (бекенд Zou випереджає Kitsu), тож порівняння під «технічно
точнішою» назвою `zou` непомітно порівнювало б із номерами не того
компонента, — звідси два зареєстровані продукти, що спільно використовують
одну реалізацію проби, а не один продукт із псевдонімом.

## Записувані поля

- `version`
- `extra.databaseUp`, `extra.keyValueStoreUp`, `extra.eventStreamUp`,
  `extra.jobQueueUp`, `extra.indexerUp` — прапорці стану компонентів,
  `"true"`/`"false"`

## Зіставлення з CVE

Не зіставляється — жодна з баз не має придатних для цього даних. Див. [Зіставлення з CVE](/uk/cve/#які-продукти-зіставляються).

## Резолвер життєвого циклу

`github:cgwire/kitsu` — лише останній реліз на GitHub; без даних
eol/support/lts (GitHub не має позиції щодо політики життєвого циклу,
лише «який тег останній»).
