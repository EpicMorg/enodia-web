Виконує `p4 -Ztag -p <address> info` — ту саму команду і той самий
механізм зовнішнього CLI, що й [`p4d`](/uk/configuration/products/p4d/);
на тій сторінці пояснено, чому проба викликає власний бінарний файл `p4`
оператора, а не працює з мережевим протоколом Perforce напряму.

```yaml
targets:
  - id: p4p-main
    product: p4p
    address: p4p.example.com:1666
```

## Потрібен CLI `p4` на машині, де запущено enodia

Так само, як для [`p4d`](/uk/configuration/products/p4d/#потрібен-cli-p4-на-машині-де-працює-enodia)
— якщо `p4` немає в `$PATH`, перевизначте шлях до бінарного файлу через
`options.binary`:

```yaml
targets:
  - id: p4p-main
    product: p4p
    address: p4p.example.com:1666
    options:
      binary: /opt/perforce/bin/p4
```

## Тайм-аут

`timeout` (для кожної цілі окремо, із запасним значенням `defaults.timeout`)
застосовується до підпроцесу `p4` так само, як до власного транспорту
будь-якої іншої проби — див.
[примітку на сторінці `p4d`](/uk/configuration/products/p4d/#тайм-аут), чому
це має конкретне значення саме для Perforce. Виправлено в 1.2.1.

## Автентифікація

Немає — підтверджено наживо, що `info` повністю відповідає без
автентифікації на реальному production-проксі.

## Перевірка ідентичності вендора

Проксі відповідає на `info` усім тим самим, що й прямий сервер, **а також
власним полем `proxyVersion`** — `serverVersion`/`ServerID`/`serverServices`
бекенд-сервера передаються без змін і описують сервер за проксі, а не сам
проксі. Ця проба вимагає наявності `proxyVersion` і відхиляє відповідь
прямого сервера (у якій такого поля немає), замість того щоб повідомити
версію не того продукту, — ту саму перевірку
[`p4d`](/uk/configuration/products/p4d/) виконує у зворотному напрямку.

## Записувані поля

- `version` — наприклад, `2024.2`, розібрана з `proxyVersion` у формі
  `P4P/LINUX26X86_64/2024.2/2832881 (2025/09/30)`
- `extra.raw` — повний нерозібраний рядок `proxyVersion`
- `extra.backendServerVersion`, `extra.backendServerID` — власні версія/ID
