Читає версію з `GET /api/version` — навмисно зі шляху без версії, а не з
конкретного `/api/v11/version`. За ці роки Perforce змінювала мінімальну
версію цього API (Swarm 2017.3 підтримує лише v7; 2018.2 — v9), а запит до
`vN` поза допустимим діапазоном отримує `401` на ендпоінті, який в іншому
разі повністю анонімний. Форма без версії позбавляє необхідності вгадувати,
який `vN` певна інсталяція ще приймає.

```yaml
targets:
  - id: swarm-main
    product: perforce-swarm
    address: https://swarm.example.com
```

## Автентифікація

Немає — ендпоінт не приймає жодного виду облікових даних.

## Розбір версії

Сире поле має вигляд `SWARM/2024.6/2710109 (2025/01/28)` — воно
розбирається на звичайну версію (`2024.6`), changelist і дату релізу. Якщо
формат не розпізнано, сирий рядок зберігається як `version` замість
повної відмови, оскільки це все одно факт, який повідомив сервер.

## Записувані поля

- `version` — наприклад, `2024.6`
- `extra.raw` — повний нерозібраний рядок
- `extra.changelist`, `extra.releaseDate` — лише якщо формат вдалося розібрати

## Зіставлення з CVE

Не зіставляється — жодна з баз не має придатних для цього даних. Див. [Зіставлення з CVE](/uk/cve/#які-продукти-зіставляються).

## Резолвер життєвого циклу

Немає — endoflife.date не має календаря під `perforce-swarm`,
`helix-swarm`, `swarm` чи `perforce` (усі підтверджено 404). Поки що лише
для інвентаризації.
