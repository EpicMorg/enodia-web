Використовує той самий механізм SSH, облікові дані та перевірку ключа хоста,
що й сімейство [ідентифікації ОС через SSH](/uk/configuration/products/ssh-os-probes/),
але — починаючи з 1.1.1 — більше не входить до спільного механізму
`osReleaseFamilyProbe`, описаного на тій сторінці; див. нижче.

```yaml
targets:
  - id: ubuntu-host
    product: ubuntu
    address: host.example.com
    credentials: linux-host-ssh
```

## Власна проба замість спільної os-release, починаючи з 1.1.1

`VERSION_ID` у `/etc/os-release` Ubuntu навмисно ніколи не змінюється після
виходу релізу — підтверджено наживо (від `14.04` до `24.10`): повністю
пропатчений хост `22.04`, який пережив кілька точкових релізів і нові
інсталяційні образи, і далі повідомляє `VERSION_ID="22.04"`, а не `22.04.5`.
Точковий реліз є лише в полі `VERSION` того самого файлу
(`VERSION="22.04.5 LTS (Jammy Jellyfish)"`), і лише для LTS-релізу, який
отримав більше одного точкового релізу, — `VERSION` не-LTS-релізу взагалі не
містить додаткового сегмента (підтверджено наживо:
`VERSION="24.10 (Oracular Oriole)"`, точно збігається з `VERSION_ID`). Ця
проба віддає перевагу номеру з `VERSION` перед `VERSION_ID` щоразу, коли він
строго точніший і має той самий префікс major.minor, — не потрібно читати
другий файл, на відміну від виправлення тієї самої прогалини для
[Debian](/uk/configuration/products/debian/), оскільки точність уже є в тому
самому файлі, просто в іншому полі. Кожен інший продукт спільного сімейства
os-release перевірено так само; жоден із решти не має цієї прогалини.

Перевірено наживо на `ubuntu:24.04`: `ID=ubuntu`, `VERSION_ID="24.04"`.

## Записувані поля

- `version` — точний точковий реліз, якщо він є у `VERSION`, напр.
  `22.04.5`; інакше просто `VERSION_ID`
- `extra.codename` — `VERSION_CODENAME` з os-release
- `extra.kernelRelease`, `extra.arch`, `extra.kernelVersion` — `uname -r`,
  `-m`, `-v`
- `packages` — встановлені бінарні пакети та їхні версії (див. нижче)
- `extra.hostKeyVerified`

## Зіставлення з CVE

Зіставляється **за кожним встановленим пакетом** з OVAL Canonical для релізу хоста (`com.ubuntu.<codename>.usn.oval.xml.bz2`, у `cve.oval.path`), а не за релізом. Проба також отримує список встановлених бінарних пакетів (`dpkg-query`) і читає `uname -r`/`-m`/`-v` за той самий обмін через SSH — це зберігається як `packages` спостереження, а також `extra.kernelRelease`, `extra.arch`, `extra.kernelVersion`. Версію запущеного ядра доповнено номером завантаження з `uname -v`, тож ядро, що вже містить виправлення, не сприймається помилково як таке, де його ще немає; знахідки для ядра називаються `kernel <flavour> (<uname -r>)`. Повідомляються лише CVE з виправленням, новішим за встановлену версію, — по одній знахідці на пакет, з посиланням на його USN. Див. [Зіставлення з CVE](/uk/cve/#cve-на-рівні-пакетів-для-дистрибутивів-linux).
