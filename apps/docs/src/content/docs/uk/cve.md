Починаючи з 2.0, enodia може повідомити, які відомі вразливості зачіпають
саме ту версію, яку повідомляє кожна ціль, — поряд з осями
патча/життєвого циклу/гілки, а не замість них. Зіставлення виконується з
двома публічними базами даних:

- **БДУ ФСТЕК** — база даних вразливостей ФСТЕК (Росія),
  [bdu.fstec.ru](https://bdu.fstec.ru/).
- **NIST NVD** — Національна база даних вразливостей США,
  [nvd.nist.gov](https://nvd.nist.gov/).

Кожна працює і сама по собі; якщо налаштовано обидві, їхні знахідки
обʼєднуються за CVE.

Починаючи з 2.2, до них долучаються власні дані безпеки чотирьох
вендорів там, де ті їх публікують: MariaDB, Atlassian (Jira, Confluence,
Bitbucket, Bamboo), PostgreSQL і nginx — див. [Власні дані
вендорів](#власні-дані-вендорів).

Починаючи з 2.1, десять дистрибутивів Linux також зіставляються **за
кожним встановленим пакетом** із власними даними безпеки їхніх вендорів —
Debian Security Tracker, OVAL-файлами вендорів і secdb Alpine (див.
[CVE на рівні пакетів для дистрибутивів Linux](#cve-на-рівні-пакетів-для-дистрибутивів-linux)).

Усе це необовʼязкове: конфігурація без блоку `cve:` поводиться точно так
само, як у 1.x, а кожне джерело працює саме по собі.

## Завантаження баз даних

enodia зіставляє лише з локальними файлами. `check`, `collect` і `serve`
ніколи нічого не завантажують — з тих самих міркувань закритої мережі,
що й у [двофазній архітектурі](/uk/concepts/#дві-фази-свідомо-розділювані):
машині, на якій запускається `check`, для зіставлення з CVE не потрібен
доступ до інтернету, лише копія файлів. Починаючи з 2.2, їх завантажує
одна окрема команда, і лише тоді, коли Ви її запускаєте: `enodia cve
update`. Або завантажте їх самі, як описано нижче для кожного джерела, —
файли в обох випадках однакові.

### `enodia cve update`

```bash
enodia cve update                         # кожен cve.*.path в активній конфігурації
enodia cve update --from inventory.jsonl  # а також те, що потрібно хостам цього інвентарю
enodia cve update --dry-run               # показати, що буде завантажено, нічого не завантажуючи
```

У кожен налаштований `cve.*.path` вона завантажує те, що читає цей запис:

- **БДУ** — `vulxml.zip`. `cve.bdu.path` тут має бути `.zip`; форми
  `.xml` і `.tar.gz`, які пошук теж приймає, — це Ваше власне
  перепакування, якого `update` не створює.
- **NVD** — файл поточного року, минулого року та будь-якого року, якого
  ще немає на диску; `--all-years` оновлює всі роки (NVD щодня
  перебудовує всі річні файли). `cve.nvd.path` має бути каталогом.
- **Debian** — `.json` трекера.
- **OVAL, secdb Alpine, сторінки PostgreSQL для окремих мажорних
  версій** — по файлу на реліз, тож релізи беруться з трьох місць: із
  файлів, які вже є в каталозі, з інвентарів, переданих через `--from`
  (які б релізи не працювали на їхніх хостах), і з `--oval`, `--alpine` та
  `--postgresql`. `cve.oval.path` і `cve.alpine.path` мають бути
  каталогами; `cve.postgresql.path`, що є файлом, отримує лише головну
  сторінку.
- **MariaDB, Atlassian, nginx** і головна сторінка PostgreSQL — по одному
  файлу.

| Прапорець | Завантажує |
|---|---|
| `--from <inventory>` | релізи OVAL, гілки Alpine і мажорні версії PostgreSQL, потрібні хостам цього інвентарю (можна повторювати) |
| `--oval <release>` | один реліз OVAL: `ubuntu:<codename>`, `rhel:<N>`, `almalinux:<N>`, `oracle-linux:<N>`, `astra-linux:<X.Y>`, `redos:<X.Y>` (можна повторювати) |
| `--alpine <branch>` | secdb однієї гілки Alpine, наприклад `v3.22` (можна повторювати) |
| `--postgresql <major>` | власну сторінку безпеки однієї мажорної версії PostgreSQL, наприклад `13` (можна повторювати) |
| `--all-years` | усі роки NVD, а не лише поточний, минулий і відсутні |
| `--dry-run` | показати, що буде завантажено, нічого не завантажуючи |

Кожен файл запитується з If-Modified-Since за його копією на диску,
завантажується в `.enodia-update/` поруч із нею, **завантажується тим
самим кодом, яким користується пошук CVE**, і лише після цього
переміщується на місце старої копії — обрізаний zip чи HTML-сторінка з
помилкою ніколи не замінять робочий файл. Незмінений файл коштує одного
запиту (MariaDB, PostgreSQL і Atlassian не надсилають Last-Modified, тож
їх завантажують знову й порівнюють). Мережеві помилки, 429 і 5xx
повторюються двічі. Одна невдача не зупиняє решту; код завершення — `1`,
якщо хоч один файл не вдалося оновити. Запускайте її з cron — наступний
цикл `check` чи `serve` підхопить нові файли.

TLS перевіряється за довіреними кореневими сертифікатами системи, плюс
те, що додає блок `cve.update`:

```yaml title="enodia.yaml"
cve:
  update:
    ca_file: /etc/enodia/russian-trusted.pem  # додається до системних коренів: PEM (один чи кілька) або DER
    ca_dir: /etc/enodia/ca                    # кожен файл сертифіката в ньому, так само
    tls_skip_verify: false                    # true: нічого не перевіряти, для кожного завантаження
```

bdu.fstec.ru цього потребує: його ланцюжок закінчується на Russian
Trusted Root CA, якого майже немає в жодному сховищі довіри, а сервер не
надсилає свій проміжний сертифікат (див. [БДУ ФСТЕК](#бду-фстек) нижче).
Без жодного з цих параметрів завантаження БДУ завершується помилкою
`certificate signed by unknown authority`, а решта все одно проходять.
Root CA і Sub CA 2024 року опубліковано за адресами
`http://nuc-cdp.digital.gov.ru/cdp/rootca_ssl_rsa2022.crt` і
`http://nuc-cdp.digital.gov.ru/cdp/subca_ssl_rsa2024.crt`; файл з обома,
обʼєднаними разом, підходить як `ca_file`.

Вона називає файли так само, як ручні команди нижче (`v3.22-main.json`,
`13.html`, …), тож обидва способи можна поєднувати. Хости, до яких вона
звертається, перелічено на сторінці [Конфіденційність](/uk/privacy/).

### БДУ ФСТЕК

Один файл — повне вивантаження ФСТЕК (близько 33 МБ у zip-архіві):

```bash
curl -fL --cacert ru-chain.pem \
  -o /var/lib/enodia/cve/bdu/vulxml.zip \
  https://bdu.fstec.ru/files/documents/vulxml.zip
```

bdu.fstec.ru використовує сертифікат національного центру сертифікації
Росії (Мінцифри), якого немає у звичайних системних сховищах довіри, —
звичайний `curl` завершується помилкою сертифіката. Крім того, сервер не
надсилає свій проміжний сертифікат, а `curl` (на відміну від браузера) не
завантажує відсутній сертифікат сам, тож установлення лише кореневого
недостатньо. Зберіть bundle з кореневого та проміжного сертифіката, який
указано в сертифікаті сайту:

```bash
curl -fsS -o root.crt https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt
curl -fsS -o sub.crt  http://nuc-cdp.digital.gov.ru/cdp/subca_ssl_rsa2024.crt
{ cat root.crt; echo; cat sub.crt; } > ru-chain.pem
```

Перевірено наживо 2026-09-23. Якщо це перестане працювати, найімовірніше,
проміжний сертифікат замінили: поточний указано в полі *Authority
Information Access* самого сертифіката сайту (`openssl s_client
-connect bdu.fstec.ru:443 | openssl x509 -noout -ext authorityInfoAccess`).
`curl -k` теж завантажить файл, але пропустить перевірку того, що Ви
збираєтеся подати у свій звіт з безпеки.

### NIST NVD

Один файл на рік, `nvdcve-2.0-<year>.json.gz`, з 2002 до поточного року.
Покладіть потрібні в один каталог:

```bash
mkdir -p /var/lib/enodia/cve/nvd && cd /var/lib/enodia/cve/nvd
for y in $(seq 2002 "$(date +%Y)"); do
  curl -fsSLO "https://nvd.nist.gov/feeds/json/cve/2.0/nvdcve-2.0-$y.json.gz"
done
```

Файл поточного року оновлюється щодня; старіші роки змінюються рідко.
Кожен файл має супровідний `.meta` (`nvdcve-2.0-<year>.meta`) з розміром і
`sha256` — зверніть увагу, що хеш рахується від *нестиснутого* JSON, а не
від `.gz`.

### Debian Security Tracker

Один файл — повне JSON-вивантаження трекера (близько 80 МБ), для цілей
`debian`:

```bash
curl -fsSL -o /var/lib/enodia/cve/debian.json \
  https://security-tracker.debian.org/tracker/data/json
```

Копії `.json.gz` і `.json.zip` теж підходять.

### OVAL вендорів

Один файл на кожен реліз дистрибутива у Вашому парку, усі в одному
каталозі, для цілей `ubuntu`, `linuxmint`, `rhel`, `rocky-linux`,
`almalinux`, `oracle-linux`, `astra-linux` і `redos`:

| Цілі | Файл |
|---|---|
| Ubuntu, Linux Mint (його база Ubuntu) | `https://security-metadata.canonical.com/oval/com.ubuntu.<codename>.usn.oval.xml.bz2` |
| RHEL **і Rocky Linux** | `https://security.access.redhat.com/data/oval/v2/RHEL<N>/rhel-<N>.oval.xml.bz2` |
| AlmaLinux | `https://security.almalinux.org/oval/org.almalinux.alsa-<N>.xml.bz2` |
| Oracle Linux | `https://linux.oracle.com/security/oval/com.oracle.elsa-ol<N>.xml.bz2` |
| Astra Linux SE 1.7, 1.8 | `https://dl.astralinux.ru/astra/oval/<1.7\|1.8>_x86-64/oval-definitions-alse-<1.7\|1.8>.xml` |
| RED OS 7.3, 8.0 | `https://redos.red-soft.ru/support/secure/<7.3\|8.0>/redos.xml` |

```bash
mkdir -p /var/lib/enodia/cve/oval && cd /var/lib/enodia/cve/oval
curl -fsSLO https://security-metadata.canonical.com/oval/com.ubuntu.noble.usn.oval.xml.bz2
curl -fsSLO https://security.access.redhat.com/data/oval/v2/RHEL9/rhel-9.oval.xml.bz2
curl -fsSL -o redos-8.0.xml https://redos.red-soft.ru/support/secure/8.0/redos.xml
```

Файли приймаються в опублікованому вигляді, `.xml` або `.xml.bz2`. Для
якого релізу призначено файл, визначається з його вмісту, а не з назви, —
тож двом файлам RED OS, обидва з яких публікуються як `redos.xml`, на
диску потрібні лише різні назви. Два файли навмисно відхиляються з
помилкою, що називає файл, який слід використати натомість:

- **Власний OVAL Rocky Linux** (`org.rockylinux.rlsa-<N>.xml`) — він
  містить лише невелику частку бюлетенів Rocky і не проходить перевірку
  схеми OVAL. Rocky перезбирає пакети Red Hat з тими самими версіями,
  тож хости Rocky зіставляються з файлом Red Hat.
- **Варіант `oci.` від Ubuntu** — він перевіряє файл стану dpkg
  регулярними виразами, а не за пакетами.

Усі URL перевірено наживо 2026-10-02.

### Alpine secdb

Два файли на кожну гілку Alpine у Вашому парку, `main` і `community`,
для цілей `alpine-linux`. У різних гілках вони мають однакові назви, тож
зберігайте їх під різними:

```bash
mkdir -p /var/lib/enodia/cve/alpine && cd /var/lib/enodia/cve/alpine
for b in v3.20 v3.22; do
  for r in main community; do
    curl -fsSL -o "$b-$r.json" "https://secdb.alpinelinux.org/$b/$r.json"
  done
done
```

### Сторінки безпеки PostgreSQL

Для цілей `postgresql`: сторінка безпеки проєкту, збережена як HTML. На
ній названо лише мажорні версії, які підтримуються сьогодні, — для
старішої мажорної версії збережіть її власну сторінку
(`/support/security/<major>/`) у той самий каталог:

```bash
mkdir -p /var/lib/enodia/cve/postgresql && cd /var/lib/enodia/cve/postgresql
curl -fsSL -o security.html https://www.postgresql.org/support/security/
curl -fsSL -o 13.html   https://www.postgresql.org/support/security/13/
```

## Конфігурація

Блок `cve:` в `enodia.yaml` — не в `settings.yaml`, оскільки він змінює
оцінювання, а не лише відображення:

```yaml title="enodia.yaml"
schemaVersion: 1
cve:
  bdu:
    path: /var/lib/enodia/cve/bdu/vulxml.zip
  nvd:
    path: /var/lib/enodia/cve/nvd
  debian:
    path: /var/lib/enodia/cve/debian.json
  oval:
    path: /var/lib/enodia/cve/oval
  alpine:
    path: /var/lib/enodia/cve/alpine
  mariadb:
    path: /var/lib/enodia/cve/mariadb.md
  atlassian:
    path: /var/lib/enodia/cve/atlassian.json
  postgresql:
    path: /var/lib/enodia/cve/postgresql
  nginx:
    path: /var/lib/enodia/cve/nginx.html
targets:
  - id: gitlab-main
    product: gitlab
    address: https://gitlab.example.com
    credentials: gitlab-token
```

| Поле | Приймає |
|---|---|
| `cve.bdu.path` | `.xml`, `.zip` (вивантаження в опублікованому вигляді) або `.tar.gz`/`.tgz` |
| `cve.nvd.path` | один файл `.json`, `.json.gz` або `.json.zip` чи каталог із такими файлами |
| `cve.debian.path` | вивантаження трекера: `.json`, `.json.gz` або `.json.zip` |
| `cve.oval.path` | один OVAL-файл (`.xml` або `.xml.bz2`) чи каталог із такими файлами |
| `cve.alpine.path` | один файл secdb `.json` чи каталог із такими файлами |
| `cve.mariadb.path` | `community-server.md` від MariaDB, збережений як є |
| `cve.atlassian.path` | JSON vuln-transparency від Atlassian, збережений як є |
| `cve.postgresql.path` | сторінка безпеки PostgreSQL як HTML чи каталог із такими сторінками |
| `cve.nginx.path` | `security_advisories.html` від nginx, збережений як є |
| `cve.update` | параметри TLS лише для [`enodia cve update`](#enodia-cve-update): `ca_file`, `ca_dir`, `tls_skip_verify` |

Відносні шляхи обчислюються відносно каталогу файлу конфігурації, у
якому їх указано, — так само, як `credentials_file`. Блок читається з тієї
конфігурації, яку фактично використовує запуск, — `--config`,
`$ENODIA_CONFIG` або [стандартні шляхи пошуку](/uk/configuration/#розташування-файлів).
Це стосується й `check --from inventory.jsonl`: інвентар, зібраний
усередині закритої мережі, зіставляється там, де запускається `check`,
якщо там знайдено конфігурацію з блоком `cve:`. Якщо конфігурацію не
знайдено взагалі, `check --from` усе одно працює, просто без CVE.

**Налаштований шлях, якого не існує, — це помилка**, а не мовчазний
пропуск: `check` завершується з `stat ...: no such file or directory`,
а не створює звіт, у якому непомітно немає жодної CVE. Починаючи з 2.1,
`enodia config validate` теж перевіряє, що кожен налаштований шлях
існує, тож помилка в шляху виявляється вже там (починаючи з 2.2, також
`cve.update.ca_file` і `ca_dir`). Чи файл справді розбирається, як і
раніше, зʼясовується лише тоді, коли запуск його завантажує, — або коли
його завантажує `enodia cve update`.

:::caution[Шляхи Windows]
Записуйте шлях Windows без лапок, в одинарних лапках, з прямими скісними
рисками або як UNC-шлях. У **подвійних** лапках YAML `\t` і `\n` стають
табуляцією та переведенням рядка — `"C:\tmp\bdu.zip"` непомітно вказував
би на інше місце, тому enodia відхиляє шлях, що містить керівний символ,
ще під час завантаження, з підказкою.
:::

## Перший запуск і кешування

БДУ і NVD розбираються потоково, а результат кешується в каталозі
кешу ОС (`$XDG_CACHE_HOME/enodia/cve`, тобто за замовчуванням
`~/.cache/enodia/cve` у Linux; `~/Library/Caches/enodia/cve` у macOS;
`%LocalAppData%\enodia\cve` у Windows). Перший запуск після зміни файлу
розбирає його повністю — близько хвилини для всього NVD разом із БДУ;
вимірювання 2026-09-23 для БДУ разом лише з файлом NVD за 2026 рік — 25 с.
Кожен наступний запуск читає кеш: 0,2 с для тих самих даних, кеш на 11 МБ.
TTL немає — ключем кешу є самі файли (розмір і час зміни) та власні
таблиці продуктів enodia, тож заміна файлу, додавання року до каталогу
NVD чи оновлення enodia кожне саме по собі запускає перебудову.

Розібраний OVAL кешується так само — близько 11 с, щоб розібрати разом
файли Ubuntu noble, RHEL 9, AlmaLinux 9 і Oracle Linux 9, переважно на
bzip2. Вивантаження трекера Debian (близько секунди на розбір) і secdb
Alpine (кілька сотень КБ) не кешуються. З усіма джерелами, налаштованими
одночасно (БДУ, NVD, Debian, вісім OVAL-файлів, Alpine), upstream виміряв
`check` приблизно в 22 с на холодну і 3,4 с з кешем, з піковим
споживанням памʼяті 0,5–0,6 ГБ — менше, якщо `cve.oval.path` містить
лише ті релізи, які у Вас справді працюють.

`enodia serve` перечитує блок `cve:` і файли на кожному циклі
`--interval` (дешево, з кешу), тож заміна файлів із cron набуває чинності
без перезапуску сервера.

## Де зʼявляються знахідки

- **`check`** — стовпець `CVES` у [поданнях `compact` і
  `drift`](/uk/views/): кількість різних CVE, що зачіпають саме цю версію.
  `-` означає відсутність знахідок — жодна не зачіпає цю версію, немає
  блоку `cve:` або enodia не зіставляє цей продукт (див. нижче); сам
  стовпець присутній завжди. `lifecycle` і `fleet` цього стовпця не
  містять.
- **`export --format html`** — той самий стовпець з інформаційним
  посиланням, що відкриває список для кожної цілі: по рядку на CVE,
  найкритичніші першими, з посиланнями на NVD, cve.org і, для знахідок
  БДУ, на сторінку bdu.fstec.ru; російський текст БДУ, якщо БДУ містить
  цю CVE, інакше — англійський опис NVD; і оцінка у вигляді кольорових
  бейджів, наприклад `CRITICAL · CVSS 3.1
  9.8`. Знахідки на рівні пакетів натомість подаються по рядку на пакет —
  `linux 6.12.107-1 → 6.12.111-1`, з посиланням на бюлетень, що містить
  виправлення, і згорнутим під ним списком CVE. Це чистий CSS —
  офлайн-звіт за замовчуванням, як і раніше, не містить жодного
  JavaScript.
- **`export --format json`** — кожна знахідка з кожного джерела повністю,
  у масиві `cves` кожної оцінки: джерело (`bdu`, `nvd` або вендора:
  `mariadb`, `atlassian`, `postgresql`, `nginx`), ID бюлетеня, ID
  CVE, заголовок, власний текст критичності від джерела, зіставлена назва
  продукту або CPE, діапазон версій і розібрана оцінка CVSS. На відміну
  від таблиці та HTML-списку, які рахують по рядку на CVE, JSON зберігає
  знахідку кожного джерела окремо — та сама CVE може зʼявитися один раз
  від БДУ і по разу на кожен відповідний CPE з NVD. Знахідки на рівні
  пакетів (джерело `debian`, `oval` або `alpine`) також містять
  встановлену й виправлену версії — див. [Звіти](/uk/reporting/#--format-json).
- **`export --format prometheus`** — без даних про CVE.

**CVE не впливають на критичність чи код завершення.** `SEVERITY`, як і
раніше, обчислюється лише з осей патча/життєвого циклу/гілки, і
`--fail-on` теж знає лише ці три осі — знахідка є фактом, на який варто
поглянути, а не вердиктом, який enodia винесла замість Вас. Чи повинна
CVE підвищувати критичність і як саме — відкрите питання в upstream.

## Які продукти зіставляються

91 зі 123 продуктів: 81 — за назвою продукту з БДУ і NVD (шість із них —
ще й із власними даними свого вендора, див. [нижче](#власні-дані-вендорів)), назву кожного
вендора/продукту перевірено дослівно на реальних повних вивантаженнях, і
10 дистрибутивів Linux — за кожним встановленим пакетом (див. наступний
розділ). Джерела для кожного продукту див. на його власній сторінці в
розділі [Налаштування продуктів](/uk/products/).

Не зіставляються, кожен — з певної причини:

- **Інші дистрибутиви Linux загального призначення** (Fedora, CentOS
  Stream, Amazon Linux, openSUSE, …) — їхні CVE є вразливостями пакетів,
  номер релізу не може сказати, які пакети відтоді оновлено, а джерела
  даних на рівні пакетів для них поки немає.
- **BSD-системи та Oracle Solaris** — NVD записує їхні рівні патчів
  (`-p5` у FreeBSD, errata в OpenBSD) у поле CPE, яке цей механізм
  зіставлення не читає; зіставлення лише за релізом позначало б повністю
  оновлений хост усіма CVE, будь-коли виправленими в цьому релізі.
- **ESXi і vCenter** — та сама проблема: майже всі їхні записи — це
  літерали на кшталт `7.0` + `update_1`.
- **TrueNAS** — занадто мало записів, і версії в них позначено інакше,
  ніж повідомляє проба.
- **Немає придатних даних у жодному з джерел** — Kitsu, Zou,
  postgres_exporter, Perforce Proxy, Perforce Helix Swarm, Supermicro BMC,
  LibreTranslate, TorrServer і Euro-Office (форк без власних записів).
- **PostHog** — його межі в NVD є git-комітами, а не версіями.
- **`generic`** — власноруч написаний парсер не має ідентичності
  продукту, за якою можна було б шукати.

## CVE на рівні пакетів для дистрибутивів Linux

Номер релізу не може сказати, які пакети на хості відтоді оновлено, тож
ці десять дистрибутивів натомість зіставляються за кожним встановленим
пакетом. Їхні проби читають встановлені пакети й запущене ядро за той
самий обмін через SSH, що й саму версію, і кожен пакет перевіряється за
власними даними безпеки його дистрибутива:

| Проба | Джерело | Ключ |
|---|---|---|
| `debian` | Debian Security Tracker | `cve.debian.path` |
| `ubuntu` | OVAL Canonical | `cve.oval.path` |
| `linuxmint` | OVAL Canonical, для його бази Ubuntu | `cve.oval.path` |
| `rhel`, `rocky-linux` | OVAL Red Hat | `cve.oval.path` |
| `almalinux` | OVAL AlmaLinux | `cve.oval.path` |
| `oracle-linux` | OVAL Oracle | `cve.oval.path` |
| `astra-linux` | OVAL Astra Linux (SE 1.7, 1.8) | `cve.oval.path` |
| `redos` | OVAL RED OS (7.3, 8.0) | `cve.oval.path` |
| `alpine-linux` | Alpine secdb | `cve.alpine.path` |

**Повідомляються лише CVE, для яких уже є виправлення, новіше за
встановлену версію**, — те, що закрило б оновлення (а для ядра —
перезавантаження). CVE, які вендор ще не виправив, не показуються: вони
однакові на кожному хості релізу, і ніхто не може з ними нічого
вдіяти, тож вони лише заховали б ті, з якими можна працювати.

**Одна знахідка на пакет, а не на CVE.** Лише одне застаріле ядро може
нести понад тисячу CVE; список за кожною CVE був би нечитабельним. Кожна
знахідка називає пакет, його встановлену версію, версію, що закриває всі
CVE в ньому, і бюлетень, який містить це виправлення (USN, RHSA, ALSA,
ELSA, бюлетень Astra, ROS або сторінка трекера Debian/Alpine). Стовпець
`CVES` і далі рахує CVE, а не пакети.

**Версії порівнюються за власними правилами кожного менеджера пакетів** —
порядком dpkg, rpm і apk, звіреним в upstream з `apt_pkg`, rpm і
apk-tools на тисячах реальних пар версій для кожного, — плюс потоки
модулів AppStream (пакет зіставляється лише з виправленнями свого
потоку), архітектура, варіанти FIPS і Ksplice в Oracle Linux, а також
**запущене** ядро, а не будь-які встановлені пакети ядра. Кожне джерело
звірено в upstream з `oscap oval eval`, `dnf updateinfo`, python3-apt або
`apk version -t` на реальних хостах і контейнерах, з ідентичними
результатами.

**Proxmox VE** отримує знахідки за пакетами як друга ціль: SSH-ціль
[`debian`](/uk/configuration/products/debian/) на тому самому хості,
поруч із його API-ціллю [`proxmox`](/uk/configuration/products/proxmox/).
Пакет Debian `linux` зіставляється лише із запущеним ядром Debian, тож
власне ядро Proxmox не сприймається за нього.

### Зіставлення з урахуванням редакції

GitLab, HashiCorp Vault, Nextcloud і MongoDB публікують окремі списки CVE
для своїх community- та enterprise-редакцій. Їхні проби записують власну
редакцію сервера в `extra.enterprise`, і community-екземпляр більше не
бачить знахідок, що стосуються лише enterprise: на реальних даних GitLab
19.2.2 CE бачить 4 з 9 записів NVD, Nextcloud 27.1.3 CE — 11 з 23. Якщо
редакція невідома (старіший сервер, який її не повідомляє), зберігаються
всі знахідки.

Починаючи з 2.2, версії ще кількох продуктів указують, до якої лінійки
чи редакції застосовується діапазон:

- **Jenkins** — щотижневі (`2.580`) і LTS-релізи (`2.568.3`) отримують
  те саме виправлення під різними номерами, і обидві бази записують
  діапазон для кожного. Лінійку визначає форма версії (дві частини —
  щотижнева, три — LTS), тож виправлений LTS більше не позначається
  щотижневою межею того самого виправлення.
- **Splunk** — застосовуються лише діапазони Splunk Enterprise (про це
  каже власний `product_type` splunkd); Splunk Cloud не зіставляється.
- **pfSense** — проба повідомляє лише Community Edition, тож діапазони
  pfSense Plus ніколи не застосовуються.
- **WAPT** — власна редакція сервера (`community` або `enterprise`)
  передається як є.
- **Kafka** — збірка Confluent Platform (`7.6.1-ccs`) не шукається: її
  власна нумерація виглядала б новішою за будь-яку межу Apache Kafka.

### Dell iDRAC і Synology DSM

**iDRAC**: обидві бази називають кожне покоління iDRAC окремим
продуктом, а номери їхніх прошивок перекриваються (iDRAC7 і iDRAC8 обидва
мають 2.x, з різними виправленнями). Покоління визначається з
`extra.model` проби — власного рядка моделі Redfish: 11G — це iDRAC6, 12G
— iDRAC7, 13G — iDRAC8, 14G–16G — iDRAC9, 17G — iDRAC10. Без моделі
шукається лише прошивка 3.x і новіша — це може бути лише iDRAC9.

**Synology DSM**: реліз — це версія, збірка й Update: Synology пише
`DSM 7.2.1-69057 Update 6`, NVD і БДУ — `7.2.1-69057-6`. Починаючи з 2.2,
проба також записує Update в `extra.update`, і обидві частини
згортаються в одну порівнювану версію. Інвентар, зібраний до 2.2, не має
`extra.update` і читається як Update 0: виправлені Update можуть бути
позначені, але жоден не буде пропущений.

### SSH

Проба [`ssh`](/uk/configuration/products/ssh/) охоплює будь-яку
реалізацію SSH, тож зіставлення виконується за банером: `OpenSSH_…`
шукається як OpenSSH, `dropbear_…` — як Dropbear, а для будь-якого іншого
SSH-стека пошук не виконується зовсім, замість того щоб позичати CVE
OpenSSH.

## Власні дані вендорів

БДУ і NVD часто описують виправлення в одній гілці як відкритий діапазон
(«before 11.4.10»), який тоді охоплює й усі старіші гілки — зокрема
виправлені релізи та гілки, де цієї вади ніколи не було. Чотири вендори
самі публікують точні дані для кожної гілки, і enodia читає їх поруч із
БДУ і NVD з одним додатковим правилом: **там, де дані вендора знають CVE,
переважає його висновок** — знахідка БДУ чи NVD, чиї CVE вендор охоплює і
для цієї версії не позначає, відкидається. CVE, яких вендор не наводить,
і далі надходять із БДУ і NVD.

| Ключ | Продукти | Джерело |
|---|---|---|
| `cve.mariadb.path` | `mariadb` | таблиця виправлених CVE від MariaDB |
| `cve.atlassian.path` | `jira`, `confluence`, `bitbucket`, `bamboo` | дані Atlassian про вразливості для кожного релізу |
| `cve.postgresql.path` | `postgresql` | сторінки безпеки PostgreSQL |
| `cve.nginx.path` | `nginx` | бюлетені безпеки nginx |

Без цих ключів продукти й далі зіставляються лише з БДУ і NVD — з
описаною вище проблемою перекриття.

### MariaDB

MariaDB одночасно підтримує пʼять-шість серій релізів. На реальних
версіях парку діапазони БДУ і NVD позначали останні, повністю оновлені
релізи підтримуваних серій (10.11.19, 11.4.13), тоді
як ті самі дві бази пропускали 9 із 21 CVE, які сама MariaDB указує для
10.11.8.

`cve.mariadb.path` додає власну таблицю виправлених CVE від MariaDB, у
якій реліз із виправленням названо **для кожної серії**. CVE, яких
таблиця не містить (новіші за Вашу завантажену копію, наявні лише в БДУ
або без ідентифікатора CVE), і далі надходять із БДУ і NVD.

Як читається таблиця:

- Серія з власним виправленням вразлива від свого першого релізу до
  цього виправлення.
- Серія без власного виправлення, яка ще підтримувалася, коли CVE
  виправили в іншій серії, не зачеплена — MariaDB виправляє всі живі
  серії разом.
- Серія, підтримка якої на той момент уже завершилася, позначається для
  кожного релізу, а релізом для переходу вказується найменше виправлення
  в новішій серії (про це повідомляє `FixStatus`). Це навмисний ухил у
  бік повідомлення, і лише для завершених серій.

### Atlassian

Експорт Atlassian містить кожен реліз Jira Software, Jira Core,
Confluence, Bitbucket і Bamboo (Server і Data Center) із CVE, які його
зачіпають, і релізом, що виправляє кожну, — **разом із CVE сторонніх
залежностей**, яких записи NVD про Atlassian ніколи не містять. Проба не
може відрізнити Server від Data Center, тож читаються обидва списки. Jira
Service Management нумерує свої релізи окремо й не зіставляється;
release candidate та EAP пропускаються.

Ціль оцінюється **в межах власної гілки major.minor**: від зачепленого
релізу до наступного, указаного як такий, що її виправляє, або до кінця
гілки, якщо виправлення не було. Jira 10.3.26 не позначається CVE, яку
Atlassian указує лише для 10.1 і 11.3. Оскільки Atlassian перелічує
релізи поодинці, її висновок діє лише для релізу, який вона перелічує, —
реліз, новіший за Вашу копію файлу, зберігає знахідки БДУ і NVD.
Upstream виміряв, що найновіший реліз кожної підтримуваної гілки не має
знахідок Atlassian, тоді як старіші отримують багато: Jira 10.3.12
перейшла з 4 CVE до 119, майже всі — залежності, виправлені в пізніших
релізах 10.3.

### PostgreSQL

Сторінка безпеки називає для кожної CVE підтримувані мажорні версії, які
вона зачіпає, і виправлення в кожній. Її висновок охоплює лише мажорні
версії, названі на збережених сторінках: головна сторінка містить лише
ті, що підтримуються сьогодні, тож для завершеної мажорної версії (13,
9.6) збережіть її власну сторінку в той самий каталог — без неї ця
версія зберігає знахідки БДУ і NVD. Мажорна версія, підтримка якої
завершилася ще до появи CVE, позначається без виправлення, якщо CVE
сягає найстарішої мажорної версії, що тоді ще підтримувалася, — як і
завершені серії MariaDB. Рядки `packaging` (інсталятор чи збірка RPM)
відстежуються, але не позначаються. Upstream виміряв, що поточні релізи
18/17/16/15/14 перейшли з до 55 знахідок БДУ кожен до жодної.

### nginx

Кожен бюлетень наводить вразливі версії і, для кожної гілки, перший
виправлений реліз (`1.31.3+, 1.30.4+`): стабільний 1.30.5 більше не
позначається діапазоном, записаним до виправлення в mainline. Гілки, які
так і не отримали виправлення, і далі позначаються; бюлетені лише для
nginx/Windows пропускаються.

## Відомі обмеження

- **БДУ може завищувати кількість знахідок між гілками.** Один запис БДУ
  часто містить окремий діапазон для кожної гілки супроводу, і всі вони
  мають спільну нижню межу, тож версія, яка вже є виправленням у своїй
  гілці, все одно може потрапити в ширший діапазон сусідньої гілки
  (задокументований приклад — Confluence 8.3.3 і CVE-2023-22515;
  діапазони Synology DSM для окремих гілок поводяться так само — DSM
  7.2.1-69057 Update 8 отримує 5 знахідок БДУ).
  Діапазони NVD для тієї самої CVE мають власні нижні межі й такої
  проблеми не мають. enodia свідомо схиляється до того, щоб повідомити
  знахідку для повторної перевірки, а не мовчки пропустити реальну.
- **Записи NVD зовсім без обмеження версій відкидаються.** За
  вимірюваннями на повних вивантаженнях, це майже завжди були CVE
  давністю в десятки років, привʼязані до поточних релізів; ціна — рідкісна
  справді невиправлена CVE, записана таким чином.
- **Покриття на рівні пакетів має власні прогалини.** Трекер Debian
  охоплює лише релізи, які ще підтримує команда безпеки Debian (bookworm,
  trixie, testing, sid), — старіші хости знахідок за пакетами не
  отримують. Alpine edge не має нумерованої гілки й теж їх не отримує.
  OVAL обчислюється не як повноцінний інтерпретатор: ключі підпису
  пакетів не перевіряються, тож сторонній пакет з назвою пакета
  дистрибутива порівнюється так, ніби він належить дистрибутиву. Пакети
  ядра Astra Linux порівнюються як встановлені, а не як запущені.
- **Умови NVD для кількох продуктів** («вразливий лише з бібліотекою Y»)
  не обчислюються — проба повідомляє один продукт на ціль, тож кожен
  вразливий запис для зіставленого продукту враховується сам по собі.
